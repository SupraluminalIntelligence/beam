Beam on a phone

A window and a remote. Never a workstation.
25 Sep 2026companion to beam-design.htmlinteractive frames below

The phone can never run a harness. It can only talk to a runner that is already online somewhere: your laptop on the desk, the Mac mini in the closet, Noah's studio machine. That is the whole product on a phone: read what the team and the agents said, steer a run, answer the agent when it stops to ask, and start the next one. Everything else stays on the desk.

Because every Beam client talks to Convex, none of this needs a tunnel, a relay, or a pairing code. A phone is a document writer like any other. What it needs is a layout that fits in one hand and a notification that lands.

Four verbs

What the phone is for

on the train
Read

The chats, grouped by workspace, with who is in them right now and which runs are live. Open one and see the record: people, agents, steps, what landed.

the reason for push
Answer

An agent stops and asks. Allow, always, deny, or type the answer. First answer in the chat wins, from anyone, on any device.

the record continues
Steer

Say something mid-run. It queues as a turn and the agent reads it when this one ends. React to a teammate. Stop a run that went sideways.

closet mini opens the pr
Dispatch

Mention an agent. Pick a machine if more than one of yours is online. The run ends with a push whether or not the phone is still awake.

Prototype

Six frames, each its own live instance. Tap around inside them. The chat frame has a run in flight: approve the command and watch it land.

Structure

One list, then push

The desktop sidebar is the phone's home screen. Everything else is a push away and a swipe back.

Home is the chat list, grouped by workspace. The desktop sidebar already shows every workspace folded open with its chats under it. The phone keeps that exactly, one column, with a sticky workspace header that carries what the desktop titlebar carries: the name, the repo count, the people focused somewhere in it, and a status square per online machine. Pinned chats float above the first workspace. Settled chats fold under a count, as they do on the desk.

A chat row says what matters when you are away. Status square, title, then one mono line: which agent is live and for how long, or who is waiting for an answer, or the last person to speak. Presence avatars on the right are the same rule as the desktop: which chat each person has focused right now, one chat per person. No tabs on the phone; the navigation stack is the tab strip.

Three tabs, no more. Chats, Inbox, You. Inbox is the notification list that lives behind the bell on the desktop. You holds the account footer menu: machines, connected harnesses, notification preferences, log out. Agents' model, effort and permission mode are not a tab; they live in the composer where the choice is made, and in workspace settings.

The chat screen is the desktop thread, narrowed. The header is the mono uppercase title with a back arrow; under it a scrolling strip of chips for the repo and branch, the machine the run is on, and the people here. Messages, activity folds, approval cards and landing cards keep their desktop shapes and their rules: activity is open while it runs and folded once done, steps are one clipped line each, colour only ever means live, needs a person, failed, or a diff.

Touch changes three things. Approval buttons become full-width 48pt cells with no keyboard hints. Reactions come from a long press, not a hover bar. The composer sits above the keyboard, and the mention popover rises from it instead of floating.

Notifications

The reason the phone exists

On the desk you notice a run finishing because the tab changes. Away from the desk, the only way Beam reaches you is a notification, so the inbox is a first-class tab and the push has to land. Four kinds, unchanged from the desktop preferences: an agent needs input, work completed, work failed or stopped, someone mentioned you.

Input requests are the ones that matter. A push that says "Claude is waiting for approval" with the command in the body, and allow and deny as notification actions where the platform allows it. Tapping the body deep-links to the card in the chat, not to the top of the chat. The inbox row keeps the same two buttons so a missed banner is still one tap.

Delivery reuses what exists. The inbox rows already carry a delivery token and the reserve and finish mutations that stop two devices from ringing for one event. The phone joins that protocol as another device: reserve, show, finish. Web Push on iOS works only for a home-screen PWA and needs a service worker plus a Convex action that posts to the push endpoint. APNs through Expo is the reliable path and the main argument for a native build.

Machines

The phone needs a runner to exist

On the desktop a runner is implicit: the app launched it. On the phone there is no local runner, so the machine becomes visible. The workspace header shows a square per online machine you can use. The chat strip names the machine a run is on. Dispatch with more than one of your machines online asks which, in a sheet, and remembers the answer per chat, matching the pinned runner the desktop already stores.

The You tab lists every machine that has a token from you: online or last seen, launched by the app or running standalone, and which harnesses are installed and signed in. When nothing of yours is online, the composer says so in the warning colour and the message still posts. Agents speak only when spoken to, and a mention with no machine is a mention waiting for one.

The always-on runner from milestone M5 is the other half of this. A phone is only useful if a machine is awake somewhere, and today the runner dies with the app. The launchd wrapper is small and it is the difference between a demo and a habit.

Decisions

Things to settle before building

Home: grouped list or a workspace switcher?
Grouped list, drawn here. It is the sidebar, so the model is one model. A switcher hides the other workspaces' live runs, which is what you want to glance at. Revisit if someone has more than four workspaces.
Tab bar or none?
Three tabs. Inbox needs a badge that is visible from any screen. A bell in the header would do it, but the You tab is the only sane home for machines, and two tabs look like a mistake.
Where do agent settings live?
In the composer chip. Tap the agent chip to change model, effort and mode for the next run. The sidebar rows on the desktop exist because there is room; the phone does not have it, and the settings only matter at dispatch.
Reactions
Long press, six emoji, same as the desktop bar. Existing reaction chips stay tappable. No swipe gestures on messages; swipe is back.
Read-only tool cards
Keep them. Study cards, job cards and landing cards are already in the chat as cards. They render as they do; the buttons that need the machine are hidden. A job awaiting approval can be approved from the phone because that is a document write.
Sign in
GitHub only. No guest on the phone; membership follows repo access and a phone is always someone's. The system browser handles the OAuth round trip and returns by deep link.
Tablet
The desktop layout. An iPad in landscape has room for the sidebar and the chat. The web build already lays out that way, and an Expo build can serve the same two-column shell above a width breakpoint.
PWA first or Expo first?
PWA first, this layout. Responsive rules over the existing web app, a manifest, and Web Push get every screen above onto a phone in days with no new packages. Expo comes when push reliability or the App Store matters; it reuses contracts and the reducer and rebuilds only the views drawn here.

Not here

What stays on the desk

  • Browser preview, local server discovery, and the hosted webview.
  • CAD viewer, simulation setup, compute job submission with local inputs.
  • Sharing a folder or a service from a machine, and signing a harness in.
  • Creating a workspace, adding a repo, and inviting. Possible on a phone, not designed for one, and rare enough to stay on the desk for now.
  • Resizable anything, keyboard shortcuts, hover states.
