Beam Build Plan

Apekshik & Noah · 2 Sep 2026 · after reading T3 Code end to end

Beam is built fresh. T3 Code is a reference, not a base. It answered the hardest question, how to ride a person's own Claude Code and Codex subscription without ever touching their credentials, and it shows a clean shape for driving harnesses and recording what they do. Beam takes those ideas and leaves the rest.

The must-have

Your subscription, your CLI, nothing stored

This is what T3 Code gets right and Beam reproduces exactly. Four mechanisms, all small.

Never log in for the user
T3 Code never runs claude auth login or codex login and never captures an OAuth callback. It spawns the harness with the user's own config and lets the CLI find its credentials the way it always does. Beam does the same. The only thing Beam ever stores about a provider is a probe result.
Point at the config dir, not HOME
For Claude, set CLAUDE_CONFIG_DIR when you need isolation and leave HOME alone, because the macOS keychain lookup lives under HOME and moving it makes the CLI say "not logged in." For Codex, CODEX_HOME selects which auth.json the CLI reads. Multi-account is later; the env vars are the whole mechanism.
Probe, don't assume
Codex: spawn codex app-server, call account/read over JSON-RPC. The answer is a tagged union: chatgpt with email and planType, apiKey, or nothing, which means "run codex login." Claude: open an Agent SDK query() with a prompt generator that never yields, read initializationResult().account for email, subscriptionType, tokenSource, then abort. Never sends a message, never spends tokens. Plan labels map from claudemax20xsubscription and friends to "Max 20x," "Pro," "Team."
Fix PATH before anything
A desktop app launched from Finder does not inherit your shell PATH, so claude and codex from nvm or Homebrew are invisible. T3 Code spawns a login shell once at boot, reads its PATH, and merges it into the process. Beam does this first thing in the runner. Without it the "connected harnesses" screen lies.
What the user sees
Settings → Connected harnesses shows each harness with installed version, sign-in state, plan, and email, refreshed every few minutes and on window focus. Not signed in shows the exact command and a button that opens Terminal with it pasted. Live account.updated and rate-limit events from the harness update the row mid-run.
Borrow / skip

What Beam takes from T3 Code

Borrow the idea, write our own

  • The adapter interface. One shape per harness: start session, send turn, interrupt, respond to approval, respond to user input, stop, event stream, resume cursor. T3's is 13 methods; ours starts at 7.
  • A normalized event vocabulary. Every harness emits the same events: session started, turn started, item started/updated/completed, content delta, request opened/resolved, turn completed, account updated. UI never sees a provider-specific shape.
  • Claude via the Agent SDK. A long-lived query() with an async prompt queue. A steer is pushing a message into the live queue; the running turn continues. Resume is resume plus resumeSessionAt. Approvals are the canUseTool callback parked on a promise until someone in the chat answers.
  • Codex via app-server. Spawn codex app-server, speak JSON-RPC: thread/start, thread/resume, turn/start, turn/interrupt. Approvals arrive as server-to-client requests and are answered by id. Regenerate types from Codex's schema rather than vendoring T3's Effect versions.
  • omp via rpc mode. Spawn omp --mode rpc, NDJSON over stdio. It has a native steer command, which is exactly Beam's steer, plus follow_up, abort, set_model, switch_session. Text arrives as message_update deltas, tools as tool_execution_start/end. Providers and logins are omp's own, stored in ~/.omp/agent; Beam probes and never logs in, same as the other two. Anthropic's policy bars Pro/Max OAuth outside Claude Code, so omp's Claude models run on an API key. Claude Code stays the only subscription route for Anthropic.
  • Commands in, events out, one writer. Clients dispatch commands; a single serialized worker turns each into events and updates projections in one transaction; everyone subscribes to the event stream and folds it locally with a pure reducer. In Beam the writer is Convex, which serializes mutations for free.
  • Streaming as deltas, coalesced. Assistant text streams as append-deltas on one message, batched every ~100ms before hitting the shared store. Convex charges per write; this is the difference between fine and expensive.
  • Worktree per chat, stacked landing. git worktree add under a Beam directory on first dispatch, then commit → push → PR as one pipeline with per-phase progress. Checkpoints as hidden git refs, not file copies.
  • Server is the execution boundary. The UI never touches git, files, or a harness. Only the runner does. This is what lets a headless runner exist later without changing the UI.
  • Capability flags in the contract. Older runner, newer app, or the reverse, must degrade rather than break.
  • Electron shell pattern. Spawn the runner as a bundled Node entry via ELECTRON_RUN_AS_NODE; renderer served over a custom protocol; electron-builder for dmg; electron-updater later.

Skip

  • Effect. T3 is Effect end to end, server and client. It's coherent and it's a language of its own. Beam is plain TypeScript with zod schemas and small pure functions. We borrow the architecture, not the library.
  • Their sync layer. Custom WebSocket RPC, pairing tokens, DPoP, Cloudflare tunnel relay, Clerk. All of it exists to get one person's devices to one server. Beam's multiplayer is Convex, which every member's app and every runner connects to directly. No relay, no tunnel, no pairing.
  • Three extra providers, mobile, marketing, terminal. Two harnesses, one desktop app. Terminal output renders as text in the run log, not a PTY emulator.
  • Their client. 21 routes and ~290 components built around a three-panel layout with a diff pane. Beam's UI is the prototype, ported to React. @pierre/diffs is a standalone MIT library worth using for the inline diff artifact.
  • Themes, keybinding editor, usage dashboards, PR review UI. The PR is the review surface.

License note. T3 Code is MIT. Where a specific piece is worth copying rather than rewriting, the login-shell PATH fix and the Windows npm-shim resolution for the Claude executable are the two candidates, keep the MIT notice with the file.

Architecture

Two planes

A shared plane that is the record, and an execution plane that is whoever's laptop dispatched the run. Convex joins them.

Shared plane
Convex. The chat is the record: every human message, dispatch, steer, approval, agent reply, activity line, artifact, and landing card is a document. Members' apps subscribe to live queries. Runners are ordinary Convex clients too, signed in as the person whose machine they run on. Mutations serialize, so "one writer" is free.
Execution plane
The runner. A standalone Node process with its own identity: registered to a workspace, owned by a person, signed in to Convex as them. The desktop app happens to launch one at startup, but nothing about the runner assumes an app is attached. It hydrates PATH, probes harnesses, and watches Convex for runs assigned to it. A dispatch by you creates a run whose runner is your machine. The runner starts the harness in the chat's worktree, streams normalized events into Convex in coalesced batches, receives steers and approval answers as documents, and lands the branch and PR. When the run ends it writes the landing card.
Why not a T3-style local server
T3 needs one because its clients are phones and browsers reaching one machine. Beam's clients all reach Convex. The runner is a client, not a server. No open ports, no pairing, no relay, and Noah steering a run on your laptop is just a document write.
Clients are thin
Anything that can reach Convex is a client. Desktop today, web and mobile later. The lesson from T3 Code: keep contracts and the event reducer in shared packages, and keep every app to rendering plus a platform bridge. Their web and mobile state files are byte-identical apart from a label. Beam's apps/web never assumes Electron, so a browser build is a config change, and an Expo app reuses packages/contracts and packages/reducer untouched. Presence, reactions, dispatch, steer, and approvals are all just Convex writes, so a phone gets them for free.
Desktop shell
Electron + React + Vite, not native. The two things that make Beam work are JavaScript: the Claude Agent SDK is a TypeScript package, and the Convex client is JavaScript. A Swift app would still need a Node sidecar for both, so you would build the IPC anyway and get none of the UI reuse. Tauri has the same sidecar problem plus a Rust layer for a two-person team to carry. How T3 Code does it: Electron, main and preload written in Effect; the renderer is not bundled into the app but served through a custom t3code:// protocol that proxies to the local server; the server is their published CLI, spawned by Electron itself with ELECTRON_RUN_AS_NODE=1; packaging via electron-builder for dmg, nsis, and AppImage; updates via electron-updater with stable and nightly channels. Beam: the same skeleton, smaller. Main process spawns apps/runner as a Node child with ELECTRON_RUN_AS_NODE, talks to it over stdio JSON lines, and exposes a small preload bridge for the renderer: harness status, open Terminal with a command, pick a folder, open external. Renderer is apps/web loaded from a bundled build in production and from Vite in dev. electron-builder for a signed, notarized dmg from day one, electron-updater in M5.
Auth and membership
GitHub sign-in through Convex Auth. A workspace is a team space with a set of connected repos. A chat attaches one repo, and the runner clones it once per machine and creates a worktree and branch on the first dispatch without the user doing anything. A new chat, team or private, starts with only its creator; inviting someone adds them to the workspace and, by default, to the current chat. The GitHub token also lets the runner open PRs via the API, with gh as a fallback.
Runner assignment
Every dispatch targets a runner. Default is the dispatcher's own online runner; otherwise the chat shows the workspace's online runners to pick from. A run stays bound to its runner for resume. If that runner goes offline the chat says so and offers to redispatch. Detached from day one: beam-runner login uses a device-code flow so a runner on a Mac mini or a server signs in without a desktop app. This is what makes a phone useful, since a phone can dispatch and steer but never runs anything.
Cost control
Content deltas batch at 100ms per message. Activity lines write once on completion, not on start, unless they last more than two seconds. Presence writes throttle to one per 20s per member.
Repo

Layout

beam/ ├── apps/desktop Electron main + preload, spawns runner, packaging ├── apps/web React UI (the prototype, componentized), Vite ├── apps/runner Node CLI: `beam-runner`, also the headless daemon later ├── packages/contracts zod schemas: chat, message, run, run event, harness event, capabilities ├── packages/harness adapter interface + claude adapter + codex adapter + probes ├── packages/git worktrees, checkpoints, commit→push→PR pipeline ├── packages/reducer pure fold of run events into a chat view (shared by app and tests) ├── convex/ schema, auth, queries, mutations, run claiming, presence └── design/ the two design artifacts, exported

Stack: pnpm workspace, TypeScript strict, Vite, React 19, Convex, zod, vitest. Electron 3x with electron-builder. The Claude adapter depends on @anthropic-ai/claude-agent-sdk; the Codex adapter depends on nothing but child_process and a JSON-RPC framing helper.

Milestones

Order of work

Each one ends with something you and Noah can use. M2 is the bar from the design doc: one real change, done in Beam, preferred over Conductor.

M0
Two people in one chat
Monorepo, Convex schema, GitHub sign-in, Electron shell loading the React app, workspaces with connected repos, chats that attach a repo, invite that adds to the chat, presence, reactions, tabs. No agents yet.
done when: you and Noah argue in a chat on two laptops and it feels like the prototype
M1
Connected harnesses, detached runner
Runner as its own process with its own identity and a device-code login, registered to a workspace, launched by the app or by hand. PATH hydration, binary discovery, Claude probe via SDK init, Codex probe via account/read, status rows with plan and email, the not-signed-in path that opens Terminal with the command, refresh on focus. Online runners visible in the workspace.
done when: both of you see "Claude Code · signed in · Max" on your own machines with zero config
M2
@claude does the work
Claude adapter: session per chat, worktree on first dispatch, normalized events streaming into the chat as "On it," folded activity, permission asks anyone can answer, final reply, branch push and draft PR, landing card. Steer by @mention mid-run with receipt. Interrupt. Resume on the next @mention.
done when: a real PR lands from a chat, with Noah steering a run on your machine
M3
@codex, then @omp
Codex adapter over app-server JSON-RPC with the same event vocabulary, approvals as request/answer pairs, resume via thread/resume. Then omp over its --mode rpc NDJSON protocol: prompt, steer, abort, switch_session map one-to-one onto the adapter, and its extension-UI confirmation frames are the approval channel. Per-agent settings: model, effort, permission mode, always-allow list.
done when: Codex reviews a PR Claude opened, and omp on a Kimi or GPT model does the same, in the same chat
M4
Private chats and artifacts
Private chats with pinned default agent and one-way share. Inline artifacts: diff from the PR via @pierre/diffs, run log, tables, diagrams as mermaid. Auto-title from the first message. Scope control in the header.
done when: you work solo in a private chat and share it without anything looking different
M5
Always-on runner, then a phone
Launchd service wrapper so a runner survives reboots on a Mac mini. Web build of apps/web. Expo app on the shared packages: read chats, dispatch, steer, approve, react. dmg with auto-update. Restyle onto the Supraluminal design language.
done when: you dispatch from your phone on the train and the closet Mac mini opens the PR
Decide

Three calls before scaffolding

Convex as the shared plane
Recommended yes. It removes the relay, pairing, and WebSocket server that make up a third of T3 Code, and you already run two products on it. The cost is per-write pricing, handled by coalescing. The alternative is our own WebSocket server per machine plus a relay, which is exactly the part of T3 we're skipping.
No Effect
Recommended. Plain TypeScript, zod at the edges, pure functions for the reducer and the decider. We lose T3's typed error channels and structured concurrency; we keep the ability to read our own code in six months.
Runner as a separate, detached process from day one
Decided. Its own identity, its own login, launched by the app or by hand. This is the thing that makes mobile possible later, because a phone can never run a harness; it can only talk to a runner that is already online somewhere.
