Product design · v0 · desktop

Beam

Argue it out. Then beam it.
Apekshik & Noah
1 Sep 2026 · working draft

A desktop app where your team and your coding agents share one chat chat. You and your teammates discuss an architectural change in the open, disagree, converge. Then someone types @claude or @codex in that same chat and the agent goes and does it, live, where everyone can watch, steer, and approve.

Today every coding agent is a one-on-one conversation. Beam makes it a room.

The paradigm

The chat is the workspace

The thing that felt new in Conductor was not the agent. It was that the argument and the execution happened in the same place. Beam builds the whole product around that one loop.

humans
Discuss

Talk like you would in Slack. Paste stack traces, link files, disagree. Nothing here goes to an agent until someone asks.

humans
Decide

The plan emerges from the conversation. No separate spec document: the last few messages are the spec.

agent
Dispatch

An @mention sends the chat's context to Claude Code or Codex. It works in a branch, in the open. Anyone can steer it mid-run.

agent → humans
Land

The run ends as a pushed branch and a PR card in the chat. The discussion picks up right where it left off, now about the diff.

Not a chat client. A workspace is a repo and the collection of chats about it. The sidebar is where workspaces live: create one, switch between them, see each one's chats nested underneath with what is running. You open a few chats as tabs, the way you open files in an editor, and close them when they land. There are no channels and no unread badges nagging you. The chrome is flat, hard-edged, and mostly monospace, so it reads as a tool, not a lounge.

Three rules keep it honest.

  • Agents only speak when spoken to. Humans chat freely. An agent reads the chat only when mentioned, and it sees everything above the mention, so "take the plan above" just works.
  • Git is the shared filesystem. Beam never syncs files between laptops. Every run happens in a git worktree on one machine and lands as a branch. Everyone else pulls.
  • One chat, one active branch, one run at a time. A chat works on one branch until its PR merges, then rotates to a fresh branch off main for the next piece, in the same worktree with the same chat as context. Two agents never edit the same branch concurrently. Parallel work means parallel chats.

What each kind of message is

Human message

Plain chat, colored per person. Never sent to an agent on its own, even while one is working in the chat.

Dispatch

A message that @mentions an idle agent. It gets a left rule. The agent receives the chat above it as context and this message as the ask.

Agent reply

The agent talks like a teammate who picked up the ticket: "On it", "Got it", "Done, take a look at #412." Its words are the message. Consecutive turns from one sender share a header, human or agent, and the header comes back whenever the sender changes.

Activity

Folded under each agent reply: the tool calls that happened, one line each, expandable to raw output. It is the receipt, not the conversation. Only the live one starts open.

Steer

An @mention of an agent that is already working. A normal message from a normal person. It queues, lands at the agent's next turn, and shows a receipt for when it was picked up. The agent answers in its own words, then continues.

Ask

The harness's permission prompt, phrased as a question from the agent. Anyone in the chat can answer. The message records who did.

Artifact

Anything that doesn't fit a chat bubble: a plan, a diagram, a diff, a table, the run log. Posted as a card in the chat. Click the card and it expands in place, click again and it folds. Humans and agents both post them.

Landing card

The branch and PR a run produced, with files touched. Every run ends with one, even a failed run, so the chat always says what state the branch is in.

How steering works. A run is one logical thing, but the chat never shows it as one block. Every time a human speaks during the run, the agent's current turn closes and whatever it does next opens under a new reply. Chronology holds, and human messages stay human messages.

  • Plain messages during a run are just chat. You and Noah can argue while Claude works without Claude reading it mid-task. It sees that conversation when the run ends or on the next dispatch.
  • @mentioning the working agent steers it. The message is queued and delivered as the agent's next user turn, after the in-flight tool call finishes.
  • Interrupt is the brake. Cancels the current tool call and delivers the message now. Stop lives on the activity header and ends the run.
  • Receipts, not guesses. A steer shows "queued" until the agent's next turn consumes it, then "picked up 14:08:31." The agent's acknowledgement is its next reply.
  • Two steers before the next turn arrive together, in order, as one user turn.

No side panel. There is one surface, the chat. Artifacts are cards that expand in place, so the record and the viewer are the same thing and the conversation always has full width. A document that matters to the whole workspace is a chat of its own, pinned at the top of the sidebar, and agents get pinned chats as context on dispatch.

Harnesses

Bring your own agent

Beam does not ship a model. It talks to the coding harnesses you already pay for, through the headless interfaces they already expose. Agents belong to the workspace, not to a person. A run happens on the machine of whoever dispatched it.

Beam desktop

  • Chat UI, presence, mentions
  • Builds the prompt: chat transcript + dispatch message + repo conventions
  • Renders agent event stream as a work card
  • Routes permission asks to the chat and answers back
spawnevents

Harness adapter

start(chat, worktree) → run

run.send(text) · run.approve(id) · run.cancel()

run.events: text · tool · ask · done

  • One adapter per harness, one normalized event shape
  • Creates the git worktree, pushes the branch, opens the PR
  • Keeps the session id so a later @mention resumes instead of restarting
stdiojson
Claude Code
Agent SDK, or claude -p with stream-json in and out. Permission callback answers come from the chat. Sessions resume by id.
Codex
Codex app-server protocol over stdio (what the IDE extension uses), codex exec --json as the fallback. Approval requests map to the same ask event.
Kimi CLI, Gemini CLI, next
Anything with a headless JSON stream gets an adapter. The adapter is the extension point, not a plugin marketplace.

An agent is a harness plus its settings. Claude Code and Codex are the harnesses. What model runs inside, how hard it thinks, and what it is allowed to do without asking are per-agent settings, set once for the workspace and shown next to the agent's name in the sidebar. They apply no matter whose machine the run lands on. Add a second Claude Code with a different model and it is a second agent with its own name.

Open by clicking an agent in the sidebar. The fields are what the harness's headless interface actually accepts, nothing invented on top.

Where a run happens: runners. Same idea as GitHub Actions runners. A runner is anything that can host a run. Every member's app registers as a runner while it is open. A headless Beam daemon on any box, a Mac mini in a closet, is a runner. A cloud sandbox per chat is a runner the workspace provisions. Dispatch picks the chat's pinned runner, else the agent's default, else the dispatcher's own machine. The chat header shows which runner is active, and the adapter does not care which kind it is.

What the agent sees. The full chat above the dispatch, rendered as a transcript with speaker names, plus the repo's own agent instructions files. Not the whole workspace history. Long chats get summarized above a cutoff, with the last messages kept verbatim because those are the spec.

Architecture

How it holds together

Desktop shell
Electron + React. Both harness SDKs are Node, the adapters spawn child processes and need PTYs, and you already live in React. Tauri is lighter but puts the adapters across a Rust boundary for no gain at this stage.
Sync layer
Convex. Chats, messages, presence, and the agent event stream are all live queries. The host machine writes agent events as they arrive. Everyone else's app subscribes. You know the stack, and it removes the need to build a relay server for v0.
Workspace and chats
Sign in with GitHub. A workspace is a team space with connected repos. A chat attaches one repo; the runner creates the worktree and branch on the first dispatch, so nobody manages branches by hand. A new chat starts with just you and people are invited in; by default an invite also adds the person to the chat you're in. Open chats are tabs, per person: which tabs you have open is your business, not shared state.
Runners
Local runners in v0, self-hosted daemon if cheap, cloud runners in v1. Local runs use each person's install and subscription login and need no infrastructure. Cloud runners survive laptops sleeping and let anyone resume, but run on API keys, so the workspace pays per token. That is the right bill for a team and the wrong one for two friends this month.
Code movement
Git only. The host runs the agent in a worktree under a Beam directory, never in the user's main checkout. Push plus PR is the only way work leaves the host. No file sync, no shared volumes.
Permissions
Anyone in the chat can answer an ask. Two people is a team of equals. The card records who answered. Per-workspace policy (host-only, or auto-allow a command list) can come later.
Private chats
Same object, one member. A private chat belongs to the workspace, gets a branch on first dispatch, and can @mention any workspace agent. Only it may pin a default agent, so plain messages dispatch without a mention. Share is one click and exposes the whole history; a shared chat never goes private again, and the pin clears on share. Each workspace's plus offers Team chat or Private chat.
Concurrency
One active run per chat. A second @mention while a run is live is a steer, not a new run. Mentioning a different agent while one is running queues it and says so in the chat.
Scope

What v0 is

The bar: you and Noah use it for a real multi-PR change and prefer it to Conductor for that one job.

In

  • One workspace per GitHub repo, invite by GitHub login
  • Team and private chats, open as tabs, presence shows which chat each person has focused
  • Connect Claude Code and Codex from the local machine, with per-agent model, reasoning effort, and permission settings
  • Dispatch, live work card, steer mid-run, permission asks in-chat
  • Worktree per chat, push branch, open draft PR, landing card
  • Resume an agent session on the next @mention in the same chat
  • Inline artifacts: diagrams, plans, diffs, tables, run log, as cards that expand in the chat
  • Local runners, plus the headless runner daemon if it fits

Not yet

  • Cloud runners · laptops and a closet box for now
  • In-app diff review · the PR is the review surface
  • More than two harnesses · adapter shape first
  • Agents talking to each other unprompted · humans dispatch
  • Multi-repo workspaces, voice, mobile
  • Permission policies, roles, admin
The name

Why Beam

A Supraluminal Intelligence product, so the name comes from the same world. A beam is light on its way somewhere, and a beamline is the shared line in a lab where the runs happen. It is also the verb for the key moment: talk it out, then beam it over. One syllable, spelled the way it sounds.

Beam

Light in transit, the beamline in a lab, and the verb for dispatch. Short, verb-able, on-brand without needing the physics explained.

Cherenkov

The glow when something exceeds light speed in a medium, and already the company's color for "live." The tightest brand tie, and nobody spells it right the first time.

Worldline

One object's path through spacetime, shared here by humans and agents. Best concept fit. Worldline SA, a payments company, holds the mark in software.

Lightcone

Exactly the context rule: the agent sees the past light cone of the dispatch. Owned in the AI community by Lightcone Infrastructure.

Parley

The working name before this was a Supraluminal product. Named the arguing well, had nothing to do with physics.

Open questions

Decide before building

  • Whose subscription runs the agent? The dispatcher's, in v0, because the run is on their machine. Fair by default: you pay for what you send. It does mean two people dispatching the same agent can get different harness versions, which the settings panel should flag. Cloud runners make this a workspace bill later.
  • How much chat goes to the agent? Everything above the mention, or from the last landing card? Proposed: everything since the last landing card, plus a summary of what came before.
  • Should a human be able to edit the agent's context before dispatch? A "preview what Claude will see" toggle on the composer is cheap and probably worth it.
  • What happens when a local runner closes the laptop mid-run? The run dies, the activity block says so, the branch has whatever was pushed. A later @mention resumes from the session id on any runner that has the worktree, which in v0 means the same machine. The headless daemon exists to make this rare.
  • Does the chat name the branch, or the other way around? Proposed: creating a chat creates the branch from the chat name. Renaming the chat does not rename the branch.
