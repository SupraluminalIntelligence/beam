Beam Compute Plane

How Claude and Codex agents in Beam run physics tools on compute Beam allocates. Agents run on the engineer's machine or on a cloud machine, always with the engineer's own provider login. Solvers run in environments on cloud machines, and results come back as live cards and viewers in the chat.

Architecture

The loop

An engineer asks for something specific. Example: a thermal-structural check of a bracket under 200 °C cycling.

  1. The agent calls machine_open("fea") and reads the environment's /beam/env.md: installed tools, versions, worked examples and known gotchas.
  2. It writes the setup into the git worktree. machine_sync pushes only changed files to the machine.
  3. It iterates with machine_exec on the chat's 4-core cloud machine: mesh, coarse solve, read diagnostics, fix. Each step takes seconds.
  4. job_estimate then job_submit on a 96-core machine posts an approval card showing the worst-case cost, for example "~12 core-hours, at most $8". The engineer approves.
  5. The job writes its results to R2. The simulation card fills in with the 3D view and the numbers from manifest.json.
  6. The agent sweeps mesh refinement and reports the grid convergence index on the stress hotspot. The engineer pushes back, and the loop starts again at step 3.

Machines

Two speeds of work need two kinds of machine. The chat's machine is small, interactive and used constantly, so it runs on serverless sandboxes. Large CPU solves are limited by memory bandwidth and sensitive to noisy neighbours, so they run on dedicated whole nodes. Agents choose from a short list.

What each environment carries

/beam/env.md and env.json: what is installed, one worked example per tool that runs in under a minute, and known gotchas. The agent reads this before anything else. Our existing OpenFOAM recipes become examples here instead of code paths in Beam.

A small beam_out Python helper that writes results in the standard layout.

A benchmark suite with known answers, run on every environment build and by an agent from a plain-language prompt. A family is marked available once its smoke tests pass and validated once agents reliably solve its benchmarks.

# every job writes this layout
beam/out/
  report.json    # named quantities, units, provenance
  fields/*.vtkhdf # or .vtu
  series/*.csv   # residuals, forces, probes
  images/*.png
  preview/       # decimated glTF/VTP, slices

Open-source tools only at first. Commercial solvers such as Ansys, COMSOL and Abaqus need a license server the customer brings. FluidX3D is excluded because its license forbids commercial use.

Decision: Modal

Modal is the only one of the four that covers chat machines, batch jobs and GPUs with one image definition. Run long solves as Modal Functions rather than Sandboxes: Sandbox CPU costs three times as much per core-second.

The gateway reaches Modal only through the ComputeExecutor interface, and images are plain OCI images. Vercel Sandbox stays the fallback for chat machines if Modal's sandboxes disappoint. It has Firecracker isolation and a good TypeScript SDK, but tops out at 8 vCPU on Pro and has no GPUs.

First checks, on the free tier

Find Modal's real CPU ceiling by creating a Sandbox with cpu=64. The docs say an oversized request is rejected with InvalidError, so this costs nothing. Measured on 27 Sep 2026: the ceiling is 64 cores, and MPI solves stop speeding up beyond about 8 processes, so Modal machines stop at 8 cores and larger ones run on EC2.

Build one image, FEniCSx on the shared base, and run the cantilever benchmark in a Modal Sandbox. Measure cold start, image pull time and the exec round trip. The $30 monthly credit covers this.

Build order

Phase 1
Gateway with the Modal adapter, the built-in fea environment, and the machine tools. This proves the loop on physics that isn't CFD.
Phase 2
Results in the standard layout, R2, and generic 3D and plot views. Move the OpenFOAM recipes into the cfd environment as worked examples.
Phase 3
Cost estimates in approval cards, Stripe credits and workspace budgets. Required before any outside startup uses it.
Phase 4
Whole-node EC2 for 96-core machines, custom environments, then more built-in environments in the order customers ask for them.
Later
Multi-node on AWS PCS, remote visualization for very large fields, a bare-metal pool once utilization is steady.

Open decisions

Pricing. Pass compute through at cost plus a margin, or bundle it into a plan. Modal already costs more than raw cloud.

Export control. Some startup engineering data falls under ITAR or EAR. That may mean US-only regions and turning some customers away. Decide before onboarding aerospace or defense teams.

Long jobs. Beam agents speak only when spoken to. A paid multi-hour job probably needs an explicit "when this finishes, continue post-processing" approval.

Repo rules. The gateway is a new process boundary. AGENTS.md needs a line saying it may call cloud providers, and nothing else in the repo may.
